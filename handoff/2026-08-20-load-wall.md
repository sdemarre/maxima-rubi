## What this session decides

Whether `rubi` can serve the *real* scenario — one maxima process, load the
system, integrate integrands of **unknown class** — given that a single process
on this build cannot hold all 2710 class-1 rules. Two candidate directions:

1. **"Fix" the matching tools** so they work with SBCL (reduce/eliminate the
   per-rule special-variable allocation that exhausts the cap), or
2. **Adopt the "large if-then-else" strategy** instead of relying on pattern
   matching (what Rubi 5 was going to do).

A previous session proposed a per-integral-subprocess strategy; it only works
for *sweeping a corpus where each integral's file is known in advance* and does
**not** serve the real "one process, unknown-class integrand" case. That
strategy is off the table for the real use.

## The load wall (the problem) — measured on both builds

- **One maxima process holds ~294–361 class-1 rules. The full class-1 set is
  2710 — a ~7.5× gap.** No per-rule optimization closes a 7.5× gap.
- **Root cause** (confirmed in the maxima source): each `defmatch`/
  `matchdeclare` allocates **SBCL special (dynamic) variables**
  (`src/matcom.lisp`, `declare (special ...)` at lines ~92, 107, 111, 356,
  418, 421, 438, 519, 539, 605). The process cap is **~1200–1600** such
  variables → **"Thread local storage exhausted"** (an **uncatchable** FATAL)
  once exceeded.
- Maxima already fights this for its own rules via `*rule-symbol-pool*`
  (`src/globals.lisp:1914-1916` — recycles symbols from deleted rules). That is
  why **`unload` releases the budget** (measured: 4×1200 patterns with unloads
  all load).
- **5.50 did NOT raise the cap.** It is a *capacity* limit, not a *speed* limit
  — 5.50's matcher-speed improvements don't touch it. Re-measured identical on
  5.50.0 (the `.out` is stamped 5.50.0).
- **Open question (probe first — it could change everything):** is the cap a
  *count* of special variables (firm) or *memory* (tunable via SBCL
  `--dynamic-space-size` / a bigger heap at build or run time)? Not yet probed.
  `SBCL_EXTRA_ARGS` is empty but settable (`src/Makefile.am:285`).
- Full measurement: `probes/load_wall/` — a six-part, self-flagging probe
  (full load FATAL; per-file parse OK in separate processes; 1200 load / 1600
  die; unload releases; prefix 7 files/294 rules ~0.52 s; prefix 8/361 FATAL),
  stamped with `build_info()`.

## Direction 1 — "fix" the matching tools for SBCL

Make `defmatch`/`matchdeclare` not exhaust the special-variable cap, so all
2710 (or far more) rules fit in one process. Angles to investigate:

- Why does each rule cost ~3.3–5.4 special variables, and can that be reduced
  (fewer `declare (special)` per pattern, lexical instead of dynamic binding,
  shared/pooled symbols)?
- Can `*rule-symbol-pool*`-style recycling be extended so the *live* set stays
  under the cap while the *total* is 2710 (a working-set / eviction scheme at
  the maxima level)?
- Is the cap a build/runtime knob (heap size, an SBCL flag via
  `SBCL_EXTRA_ARGS`, a maxima build option) — i.e. the count-vs-memory probe
  above?
- How far would patching `src/matcom.lisp` (or SBCL) need to go? (Source at
  `~/src/external/maxima`; installed 5.50.0 at `/home/serge/local/bin/maxima`.)
- Risk: this is a maxima/SBCL-level change; the matcher's correctness must be
  preserved (the runner contract is specified in
  `docs/pattern-matching-feasibility.md` (T2), §3 trap catalog + §4 contract).

## Direction 2 — the "large if-then-else" strategy (Rubi 5)

Replace pattern matching with compiled if-then-else code. **Read the reference
first: `reference/rubi-5/Plan for Implementing Rubi 5.md` + `Rubi-5.m`.**

- Rubi 5 compiles Rubi 4's 3000+ algebraic pattern rules into **42 `Int*nnn`
  functions**, each a **single deeply-nested if-then-else construct** —
  explicitly *not* pattern matching. That is the key: **no `defmatch`/
  `matchdeclare` → no special variables → no TLS cap → all rules fit in one
  process.**
- The `Int[u, x]` dispatcher categorizes `u` (a type number: 1=linear,
  2=quadratic, 3=cubic, 4=quartic, 5=binomial, 6=trinomial, 7=unknown) and
  descends a **42-leaf if-then-else decision tree** to call the right
  `Int*nnn`. Products `Int[f^m g^n …]` sort the base/degree pairs by type
  number, then descend the tree.
- Only **~42 pattern rules** remain (vs 2710) — trivially within the cap.
- `Int111` and `Int121` are fully implemented in `Rubi-5.m` (manually compiled
  from Rubi 4 `1.1.1` and `1.2.1`); the other 40 are `Defer[Int*nnn]`
  placeholders. The author says a pattern-matching→if-then-else **compiler** is
  the intended automation, and that he has programs translating if-then-else
  decision trees from Mathematica to **Maxima** syntax.
- Implication for our codebase: this **fundamentally changes the runner and the
  generator's output** — instead of emitting `matchdeclare`/`defmatch`/
  `_mr_rule_*`, the generator would emit if-then-else `Int*nnn` functions + a
  decision-tree dispatcher. Tasks 7–10 (utility layer, corpus driver, full
  run) would be re-scoped around it.
